PostureAI 개발 스택 정리
========================

작성 목적
---------
이 문서는 PostureAI 프로젝트에 사용된 기술을 이해하고 기술 면접을 준비하기 위한 문서이다.
기술 이름만 외우지 않고 다음 네 가지를 설명할 수 있는 상태를 목표로 한다.

1. 이 기술은 무엇인가?
2. PostureAI의 어디에 사용했는가?
3. 왜 이 기술을 선택했는가?
4. 장점과 한계는 무엇인가?


1. 전체 기술 구조
-----------------

사용자
  → Vercel에서 PostureAI 웹사이트를 받는다.
  → 브라우저에서 Next.js와 React 코드가 실행된다.
  → 웹캠 영상은 사용자의 브라우저에서 처리된다.
  → MediaPipe Pose가 신체 랜드마크 좌표를 찾는다.
  → 자체 분석 코드가 좌표로 자세 각도와 점수를 계산한다.
  → React가 분석 결과를 화면에 표시한다.
  → Firebase가 로그인, 사용자 설정, 측정 기록과 이미지를 저장한다.

중요한 점:
MediaPipe가 자세 점수를 직접 만들어 주는 것은 아니다.
MediaPipe는 신체 좌표를 찾고, PostureAI의 분석 코드가 그 좌표를 이용해 점수를 계산한다.


2. HTML
-------

정의:
웹페이지의 제목, 버튼, 입력창, 문단 같은 구조를 만드는 언어이다.

프로젝트에서의 역할:
React의 JSX를 통해 화면의 구조를 작성하는 데 사용한다.

선택 이유:
웹브라우저에서 화면을 구성하는 기본 기술이기 때문이다.

면접 답변:
"HTML은 웹페이지의 구조를 만드는 언어입니다. PostureAI에서는 JSX를 통해 버튼,
카메라 영역, 점수 카드, 기록 화면 등의 구조를 작성했습니다."


3. CSS와 Tailwind CSS
---------------------

CSS 정의:
색상, 크기, 간격, 정렬, 반응형 화면 등 웹페이지의 디자인을 담당하는 언어이다.

Tailwind CSS 정의:
미리 정해진 작은 CSS 클래스를 조합하여 화면을 꾸미는 CSS 프레임워크이다.

프로젝트 적용 위치:
- app/globals.css
- components/posture-coach-app.tsx의 className

선택 이유:
- 컴포넌트 안에서 스타일을 빠르게 작성할 수 있다.
- 일정한 간격과 색상 규칙을 유지하기 쉽다.
- 반응형 화면을 작성하기 편리하다.

장점:
- 별도의 CSS 이름을 계속 만들지 않아도 된다.
- 화면 수정 속도가 빠르다.
- 사용하지 않는 스타일을 줄이기 쉽다.

한계:
- className이 길어지면 JSX를 읽기 어려워질 수 있다.
- 같은 클래스 조합이 반복되면 컴포넌트로 분리해야 한다.

면접 답변:
"Tailwind CSS는 작은 스타일 클래스를 조합해서 UI를 만드는 CSS 프레임워크입니다.
PostureAI에서는 화면을 빠르게 구성하고 일관된 간격과 반응형 디자인을 적용하기 위해
사용했습니다."


4. JavaScript
-------------

정의:

프로젝트에서의 역할:
- 버튼 클릭 처리
- 카메라 실행과 종료
- 자세 데이터 계산
- 화면 상태 변경
- Firebase 데이터 요청
- 타이머와 알림 처리

우선 공부할 개념:
- 변수와 자료형
- 조건문
- 반복문
- 함수
- 배열
- 객체
- 비동기 처리
- Promise
- async와 await

면접 답변:
"JavaScript는 웹페이지의 동작을 담당하는 언어입니다. PostureAI에서는 카메라 제어,
자세 분석 결과 처리, 사용자 이벤트와 Firebase 통신에 사용했습니다."


5. TypeScript
-------------

정의:
JavaScript에 타입 검사 기능을 추가한 언어이다.

프로젝트 적용 위치:
- components/posture-coach-app.tsx
- lib/types.ts
- lib/posture-analysis.ts
- lib/stretch-analysis.ts
- lib/firebase.ts

주요 사용 예:
- Settings: 사용자 설정의 데이터 형태
- PostureResult: 자세 분석 결과의 데이터 형태
- SessionSummary: 측정 세션 기록의 데이터 형태
- HistoryGroup: 날짜별 기록의 데이터 형태

선택 이유:
자세 분석 결과, 사용자 설정, 기록처럼 구조가 복잡한 데이터에서 실수를 줄이기 위해
사용했다.

장점:
- 실행 전에 잘못된 데이터 형태를 찾을 수 있다.
- 함수가 어떤 값을 받고 반환하는지 알기 쉽다.
- 코드 자동완성과 리팩토링이 편리하다.

한계:
- 타입을 처음 배울 때 코드가 복잡하게 느껴질 수 있다.
- 타입이 맞아도 실제 실행 중 발생하는 모든 오류를 막아 주지는 않는다.

면접 답변:
"TypeScript는 JavaScript에 타입 검사를 추가한 언어입니다. PostureAI는 자세 결과와
세션 기록의 데이터 구조가 복잡하기 때문에 타입을 미리 정의해 잘못된 값이 사용되는
문제를 줄이기 위해 선택했습니다."


6. React 19
-----------

정의:
사용자 인터페이스를 컴포넌트 단위로 만들고 상태 변화에 따라 화면을 갱신하는
JavaScript 라이브러리이다.

프로젝트에서의 역할:
- 홈, 자세 분석, 스트레칭, 기록 화면 구성
- 카메라 실행 상태 관리
- 실시간 자세 점수 표시
- 선택한 탭과 설정 관리
- 모달과 알림 표시

핵심 개념:

1) 컴포넌트
재사용할 수 있는 화면 단위이다.

2) JSX
JavaScript 또는 TypeScript 안에서 HTML과 비슷한 화면 구조를 작성하는 문법이다.

3) props
부모 컴포넌트가 자식 컴포넌트에 전달하는 값이다.

4) state
컴포넌트 내부에서 바뀔 수 있으며 화면에 반영되는 값이다.

5) useState
화면에 반영되어야 하는 상태를 관리한다.

예:
const [isRunning, setIsRunning] = useState(false);

isRunning은 분석 실행 여부이고, setIsRunning은 그 값을 변경하는 함수이다.
값이 바뀌면 React가 관련 화면을 다시 렌더링한다.

6) useEffect
렌더링 외부의 작업을 실행하고 정리한다.
예: 로그인 상태 구독, 브라우저 이벤트 연결, 설정 불러오기

7) useRef
값이 바뀌어도 화면을 다시 렌더링할 필요가 없는 값이나 DOM 요소를 보관한다.
예: video, canvas, MediaPipe 객체, 타이머, 최신 상태값

8) useCallback
함수를 재사용하여 불필요하게 새로운 함수가 만들어지는 것을 줄이는 데 사용한다.

9) useMemo
계산 결과를 재사용하여 불필요한 재계산을 줄이는 데 사용한다.

선택 이유:
실시간으로 변하는 자세 점수, 카메라 상태, 기록과 설정을 화면에 반영하기 편리하기
때문이다.

장점:
- 기능을 컴포넌트 단위로 나눌 수 있다.
- 상태가 바뀌면 화면을 자동으로 갱신한다.
- 사용자 상호작용이 많은 화면을 만들기 좋다.

한계:
- 상태와 effect가 많아지면 실행 흐름이 복잡해질 수 있다.
- 불필요한 렌더링을 관리해야 한다.
- 큰 컴포넌트는 기능별로 분리할 필요가 있다.

면접 답변:
"React는 상태에 따라 사용자 인터페이스를 갱신하는 라이브러리입니다. PostureAI는
카메라 상태와 자세 점수가 계속 바뀌기 때문에 React 상태 관리가 적합하다고
판단했습니다."


7. Next.js 15
-------------

정의:
React를 기반으로 페이지 구조, 라우팅, 빌드, 렌더링과 배포 기능을 제공하는
프레임워크이다.

React와의 차이:
- React: 화면을 만드는 라이브러리
- Next.js: React를 이용한 웹 애플리케이션의 전체 구조를 제공하는 프레임워크

프로젝트 적용 위치:
- app/page.tsx: 기본 페이지
- app/layout.tsx: 전체 페이지 공통 구조
- app/globals.css: 전역 스타일
- components/posture-coach-app.tsx: 핵심 클라이언트 화면

"use client"의 의미:
해당 컴포넌트가 브라우저에서 실행되어야 한다는 뜻이다.
PostureAI는 카메라, 브라우저 알림, localStorage, React 상태와 이벤트를 사용하므로
핵심 컴포넌트에 "use client"가 필요하다.

선택 이유:
- React 프로젝트의 파일과 페이지 구조를 관리하기 쉽다.
- 빌드와 배포 환경이 잘 갖춰져 있다.
- Vercel과 자연스럽게 연동된다.
- 나중에 페이지나 서버 기능을 추가하기 좋다.

장점:
- 파일 기반 라우팅
- 빌드 최적화
- 정적 페이지와 서버 기능 지원
- Vercel 자동 배포

한계:
- 서버 컴포넌트와 클라이언트 컴포넌트의 차이를 이해해야 한다.
- 현재 PostureAI는 클라이언트 기능이 많아 Next.js 서버 기능을 많이 활용하지 않는다.

면접 답변:
"Next.js는 React를 기반으로 라우팅과 빌드, 렌더링 구조를 제공하는 프레임워크입니다.
PostureAI에서는 App Router로 페이지 구조를 만들고 Vercel에 쉽게 빌드하고 배포하기
위해 사용했습니다."


8. MediaPipe Pose
-----------------

정의:
카메라나 이미지에서 사람의 신체 주요 지점을 감지하는 머신러닝 기반 라이브러리이다.

랜드마크:
귀, 어깨, 팔꿈치, 손목, 골반, 무릎처럼 신체의 특정 위치를 나타내는 점이다.

주요 값:
- x: 화면에서 가로 위치
- y: 화면에서 세로 위치
- z: 카메라를 기준으로 한 상대적인 깊이
- visibility: 해당 지점이 얼마나 잘 보이는지를 나타내는 신뢰도

프로젝트에서의 역할:
- 웹캠 영상에서 신체 랜드마크 감지
- 감지한 좌표를 자세 분석 코드에 전달
- 화면 위에 신체 연결선 표시

자세 점수 계산 과정:
1. MediaPipe가 귀, 어깨, 골반 등의 좌표를 감지한다.
2. visibility가 낮은 좌표를 제외하거나 측정 불가로 처리한다.
3. 좌표를 이용해 목과 상체의 기울기를 계산한다.
4. 계산값을 자체 기준과 비교한다.
5. 목, 상체, 안정성 점수와 피드백을 만든다.

개인정보 측면:
현재 자세 추론은 사용자의 브라우저에서 실행된다.
따라서 분석을 위해 실시간 카메라 영상을 별도 AI 서버에 계속 전송하는 구조가 아니다.
다만 저장 기능을 통해 생성한 이미지나 기록은 사용자의 동작에 따라 Firebase에
저장될 수 있다.

장점:
- 별도의 AI 모델 학습 없이 신체 좌표를 감지할 수 있다.
- 브라우저에서 실행할 수 있다.
- 실시간 처리가 가능하다.
- 영상을 분석 서버로 계속 전송하지 않아도 된다.

한계:
- 조명, 카메라 위치, 가림과 체형에 따라 오차가 발생한다.
- 감지 결과가 의료적 진단 수준의 정확도를 보장하지 않는다.
- 모델 파일로 인해 최초 로딩 용량이 커질 수 있다.

면접 답변:
"MediaPipe Pose는 웹캠 영상에서 신체 랜드마크 좌표를 감지합니다. MediaPipe가
자세 점수를 직접 계산하는 것은 아니고, PostureAI가 감지된 귀, 어깨, 골반 등의
좌표로 각도를 계산해 자체 기준에 따라 점수와 피드백을 생성합니다."


9. 자세 분석 로직
-----------------

프로젝트 적용 위치:
- lib/posture-analysis.ts

역할:
- 랜드마크 표시 가능 여부 확인
- 목 기울기 계산
- 상체 기울기 계산
- 움직임을 이용한 안정성 계산
- 항목별 점수와 종합 점수 계산
- 점수에 따른 피드백 생성

분석 과정:
신체 좌표
  → 필요한 좌표가 보이는지 확인
  → 각도와 움직임 계산
  → 기준 구간과 비교
  → 영역별 점수 생성
  → 종합 점수와 피드백 생성

주의할 점:
한 프레임의 값만 사용하면 카메라 노이즈 때문에 점수가 크게 흔들릴 수 있다.
그래서 최근 측정값을 일정 구간 보관하거나 평균을 사용하여 값을 안정화한다.

면접 답변:
"MediaPipe의 좌표를 그대로 화면에 표시하는 데서 끝내지 않고, 귀와 어깨, 골반의
상대 위치로 목과 상체 기울기를 계산했습니다. 순간적인 좌표 흔들림을 줄이기 위해
최근 측정값을 활용하고, 계산한 값에 따라 영역별 점수와 피드백을 생성합니다."


10. 스트레칭 분석
-----------------

프로젝트 적용 위치:
- lib/stretch-analysis.ts
- lib/stretch-guide.ts
- lib/stretch-recommendation.ts

각 파일의 역할:
- stretch-analysis.ts: 사용자 동작과 목표 자세를 비교하고 점수 계산
- stretch-guide.ts: 가이드 자세 생성, 개인 보정, 캔버스 표시
- stretch-recommendation.ts: 자세 기록을 기반으로 스트레칭 우선순위 추천

동작 과정:
1. 현재 자세 문제나 과거 기록을 확인한다.
2. 개선이 필요한 신체 영역을 선택한다.
3. 해당 영역에 맞는 스트레칭을 추천한다.
4. 사용자의 신체 좌표를 가이드 자세와 비교한다.
5. 정확도와 교정 메시지를 표시한다.

한계:
- 사용자의 유연성과 신체 조건이 모두 다르다.
- 2차원 카메라만으로 정확한 3차원 동작을 판단하기 어렵다.
- 가이드 동작의 안전성을 의료적으로 검증한 것은 아니다.


11. Firebase
------------

정의:
Google이 제공하는 애플리케이션 백엔드 서비스이다.
서버를 처음부터 직접 만들지 않고 로그인, 데이터베이스와 파일 저장 기능을 사용할 수
있다.

프로젝트 적용 위치:
- lib/firebase.ts
- firestore.rules
- storage.rules

사용 중인 기능:

1) Firebase Authentication
사용자가 누구인지 확인한다.
PostureAI에서는 Google 로그인에 사용한다.

2) Cloud Firestore
문서 형태로 데이터를 저장하는 NoSQL 데이터베이스이다.
사용자 설정, 분석 세션, 점수 기록과 알림 기록 등을 저장한다.

3) Firebase Storage
이미지 같은 파일을 저장한다.
자세 스냅샷 이미지 저장에 사용한다.

4) Security Rules
로그인한 사용자가 자신의 데이터에만 접근하도록 제한한다.

사용자 데이터 구분:
로그인 후 발급받는 UID를 사용자 식별자로 사용한다.
예를 들어 users/{uid}/sessions/{sessionId}와 같은 구조로 사용자별 세션을 분리한다.

선택 이유:
- 별도 백엔드 서버 없이 인증과 저장 기능을 구현할 수 있다.
- 웹 애플리케이션과 연동하기 쉽다.
- 소규모 프로젝트를 빠르게 개발하기 좋다.

장점:
- 로그인 기능 구현이 편리하다.
- 실시간 및 비동기 데이터 처리가 쉽다.
- 서버 관리 부담이 작다.
- 사용자별 데이터 구조를 만들기 쉽다.

한계:
- 읽기와 쓰기 횟수가 증가하면 비용이 발생할 수 있다.
- 잘못된 보안 규칙은 데이터 노출로 이어질 수 있다.
- Firebase 구조에 대한 의존도가 높아질 수 있다.

Firebase API Key 질문:
웹용 Firebase API Key는 브라우저에서 사용되므로 완전한 비밀값으로 보호되는 구조가
아니다. 실제 데이터 보안은 Authentication, Firestore Rules와 Storage Rules로
설정해야 한다.

면접 답변:
"Firebase는 로그인과 사용자별 데이터 저장을 위해 사용했습니다. Authentication으로
사용자를 확인하고, UID를 기준으로 Firestore에 측정 기록과 설정을 분리해 저장합니다.
이미지는 Storage에 저장하며 실제 접근 권한은 Firebase 보안 규칙으로 제한합니다."


12. Recharts
------------

정의:
React에서 그래프를 만들기 위한 차트 라이브러리이다.

프로젝트에서의 역할:
- 자세 점수 변화 그래프
- 세션별 기록 시각화

선택 이유:
- React 컴포넌트 방식으로 차트를 작성할 수 있다.
- 데이터 배열을 그래프에 연결하기 쉽다.
- 축, 선, 툴팁 등을 제공한다.

한계:
- 데이터가 지나치게 많으면 렌더링 비용이 커질 수 있다.
- 복잡한 디자인을 구현할 때 추가 설정이 필요하다.

면접 답변:
"Recharts는 React에서 데이터를 그래프로 표현하기 위한 라이브러리입니다. PostureAI의
날짜별 또는 세션별 자세 점수 변화를 사용자가 쉽게 확인하도록 시각화하는 데
사용했습니다."


13. Lucide React
----------------

정의:
React에서 사용할 수 있는 아이콘 라이브러리이다.

프로젝트에서의 역할:
홈, 분석, 스트레칭, 기록, 설정과 각종 상태 아이콘을 표시한다.

선택 이유:
- 아이콘 스타일이 일관적이다.
- SVG 기반이라 크기를 변경해도 선명하다.
- React 컴포넌트로 쉽게 사용할 수 있다.

면접에서는 핵심 기술보다 중요도가 낮으므로 역할과 선택 이유 정도만 설명하면 된다.


14. Git
-------

정의:
코드의 변경 이력을 저장하고 이전 상태와 비교할 수 있는 버전 관리 도구이다.

주요 개념:
- repository: 프로젝트와 변경 이력을 보관하는 저장소
- commit: 특정 시점의 변경 내용을 기록
- branch: 독립적으로 작업하기 위한 코드 흐름
- merge: 서로 다른 변경 흐름을 합침
- push: 로컬 커밋을 원격 저장소에 전송
- pull: 원격 저장소의 변경을 가져옴

면접 답변:
"Git은 코드 변경 이력을 관리하는 도구입니다. 기능 단위로 변경 사항을 커밋하고,
문제가 생겼을 때 변경 내용을 비교하거나 이전 기록을 확인하는 데 사용했습니다."


15. GitHub
----------

정의:
Git 저장소를 인터넷에 보관하고 협업할 수 있도록 제공하는 서비스이다.

Git과의 차이:
- Git: 버전 관리 도구
- GitHub: Git 저장소를 온라인에서 관리하는 서비스

프로젝트에서의 역할:
- 소스 코드 원격 보관
- 변경 이력 관리
- Vercel 자동 배포 연결


16. Vercel
----------

정의:
Next.js를 포함한 웹 애플리케이션을 빌드하고 배포하는 클라우드 플랫폼이다.

배포 과정:
1. 로컬에서 코드를 수정한다.
2. Git으로 변경 사항을 커밋한다.
3. GitHub의 main 브랜치에 push한다.
4. Vercel이 변경을 감지한다.
5. 패키지를 설치하고 Next.js 프로젝트를 빌드한다.
6. 생성된 웹 파일을 CDN에 배포한다.
7. 사용자는 HTTPS 주소로 서비스에 접속한다.

선택 이유:
- Next.js와 연동이 자연스럽다.
- GitHub에 push하면 자동으로 배포할 수 있다.
- HTTPS와 CDN이 자동으로 적용된다.
- 배포마다 미리보기 주소를 만들 수 있다.

Firebase와 역할 차이:
- Vercel: 웹사이트 화면과 정적 파일 배포
- Firebase: 로그인, 데이터베이스와 이미지 저장

한계:
- 무료 Hobby 플랜은 개인·비상업 용도이다.
- 사용량이 증가하거나 상업 서비스가 되면 비용을 검토해야 한다.
- MediaPipe처럼 큰 파일이 많으면 전송량과 초기 로딩을 관리해야 한다.

면접 답변:
"Vercel은 Next.js 웹사이트를 빌드하고 배포하기 위해 사용했습니다. GitHub의 main
브랜치에 코드를 push하면 자동으로 배포되고, HTTPS와 CDN이 적용됩니다. 웹 화면은
Vercel이 담당하고 로그인과 데이터 저장은 Firebase가 담당하도록 역할을
분리했습니다."


17. npm
-------

정의:
JavaScript 패키지를 설치하고 프로젝트 명령을 실행하는 도구이다.

프로젝트에서의 역할:
- React, Firebase, Recharts 같은 라이브러리 설치
- 개발 서버 실행
- TypeScript 검사
- 배포 빌드

주요 명령:
npm install
  필요한 패키지를 설치한다.

npm run dev
  개발용 서버를 실행한다.

npm run typecheck
  TypeScript 오류를 검사한다.

npm run build
  배포 가능한 형태로 프로젝트를 빌드한다.

package.json:
프로젝트 이름, 명령과 사용 중인 패키지 정보를 기록하는 파일이다.

package-lock.json:
설치되는 패키지의 정확한 버전을 고정하여 다른 컴퓨터에서도 비슷한 환경을 만들도록
돕는 파일이다.

20. 프로젝트의 현재 기술적 한계
--------------------------------

1. 핵심 컴포넌트가 매우 크다.
화면, 카메라 제어, 분석 흐름과 Firebase 처리가 한 파일에 많이 모여 있어 유지보수가
어렵다.

2. MediaPipe 정적 파일 용량이 크다.
최초 접속 시 모델 로딩 시간이 길어질 가능성이 있다.

3. 카메라 환경에 따라 정확도가 달라진다.
조명, 카메라 각도, 신체 가림과 사용자 체형에 영향을 받는다.

4. 의료적 정확도를 보장하지 않는다.
자세 참고와 습관 개선을 위한 도구이며 의료 진단 서비스가 아니다.

5. Firebase 비용을 관리해야 한다.
사용자가 늘면 데이터 읽기, 쓰기와 파일 저장 비용이 증가할 수 있다.

6. 실제 사용자 검증이 더 필요하다.
다양한 사용자와 환경에서 정확도 및 사용성을 측정해야 한다.


21. 개선 방향
-------------

1. 화면별 컴포넌트 분리
2. 카메라와 MediaPipe 로직을 커스텀 훅으로 분리
3. Firebase 데이터 처리를 별도 계층으로 정리
4. 사용하지 않는 MediaPipe 모델 제거 가능성 검토
5. 모델 지연 로딩과 브라우저 캐시 적용
6. Firebase 쓰기 횟수와 데이터 조회 범위 최적화
7. 다양한 사용자 대상 정확도 테스트
8. 분석 기준과 한계 문서화
9. 핵심 계산 함수에 자동 테스트 추가


22. 공부 우선순위
-----------------

1단계: 전체 실행 흐름
2단계: 변수, 조건문, 함수, 배열과 객체
3단계: React 컴포넌트와 useState
4단계: useEffect와 useRef

6단계: MediaPipe 랜드마크와 자세 점수 계산
7단계: Firebase 로그인과 데이터 저장
8단계: Next.js의 페이지 구조와 use client
9단계: Git, GitHub와 Vercel 배포
10단계: 프로젝트 한계와 리팩토링 방향

--------------------------------

- 기술 이름만 말하지 말고 실제 사용 위치를 함께 설명한다.
